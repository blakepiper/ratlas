## Budget and observer prerequisite

Each observer currently has two other candidate subjects. At 20 other-subject
requests/hour its theoretical minimum first-pass drain is 2/20 = 0.1 hours
(six minutes), before spacing, failures and health work. With 100 total subjects,
99 other-subject reads would need at least 4.95 hours per observer; with 10,000,
9,999 reads need 499.95 hours. The maximum is 480 such reads/day/source.
These are capacity lower bounds, not observed completion forecasts or daily
refresh guarantees. No quotas were increased and no duplicate sources were added.

An operator must supply an **already-running dedicated public-only observer**,
with explicit absolute executable, home and socket paths and a reviewed observer
NID. Set `localObserverPublication: "public-only-observer"` only after verifying
that its routing knowledge is publishable; otherwise retain quarantine or disable
CLI collection. Setup and daemon ownership remain with the operator.

The existing pinned adapter `heartwood-341982110-v1` requires read-only
`rad --version` and help/capability checks, `rad self --home`,
`rad node status --only nid`, and `rad node routing --json` producing bounded
NDJSON `{rid,nid}` records. When supported, `rad node events` supplies pinned
seed/inventory/node event shapes and independent timestamps. Before live use,
verify the actual deployed CLI schema, snapshot completeness, event ordering,
snapshot/event race handling, reconnect reconciliation and public-only policy.
Fixture tests exercise these behaviors; live CLI compatibility is unverified.
A supplied observer must expose enough real public subjects to meet the unchanged
100-node and five-subject journey targets; simply adding a fourth observer does
not establish that.
